# 全局工作流项目化适配：调研与实施计划

> **文档代码**：`WORKFLOW_ADAPTATION_PLAN.md`  
> **版本**：`v1.0`  
> **调研日期**：2026-11-07  
> **适用对象**：[`计划工作流.md`](./计划工作流.md)、[`程序修复工作流.md`](./程序修复工作流.md)、[`UI审美与开源组件借鉴工作流.md`](./UI审美与开源组件借鉴工作流.md) 组成的工作流包。  
> **本轮目标**：解决 Agent 能按流程修代码，却不理解项目第一要义、代码存在原因和稳定行为保护范围的问题；同时让通用工作流进入任何项目后，能生成该项目专属的、可版本管理的契约层。

---

## 1. 问题定性

用户遇到的典型故障是：一个已经稳定运行的版本被独立审查为“漏洞百出”，Agent 按局部建议逐条“修正”后，产生更多缺陷，并失去原有速度与稳定性。其根因不是流程不够多，而是几类上下文缺失叠加：

1. **缺少项目第一要义**：同声传译项目的稳定性、准确性、快速性，游戏项目的可玩性与安全性，前端项目的审美与交流感，不可能由同一套默认验收优先级代替。
2. **缺少设计意图**：一段代码单看可能不符合通用最佳实践，但在实时流、降级路径、延迟预算、兼容契约或有状态系统中是必要且自洽的。
3. **缺少“不退化”证据**：既有测试、核心路径、性能基线未与旧版本绑定，局部绿灯不能证明全局没有变坏。
4. **审查建议被当成结论**：看门狗、代码审查和静态工具输出的应是待验证假设，Agent 不应无条件照单修改。
5. **UI 与工程规则可能压过项目目标**：通用按钮、动效、音效规则是候选能力，不应自动成为所有项目的强制出厂标准。

因此，本方案不把“理解项目”寄托在一次性读懂全部源码，也不承诺零回归；而是建立可持续维护的项目契约、修改前证据基线、逐条裁决审查意见，以及明确的“未验证不得宣称通过”规则。

### 2.2 现有工作流的具体缺口

- `.agents/workflow.config` 主要记录语言、许可证、测试命令，没有 `CONTRACT_PATH`、核心回归命令、冒烟命令、性能阈值与“该项目最在意什么”。
- 看门狗的“四件套白纸输入包”不含项目契约和设计原因，白纸视角容易退化成脱离语境的通用规范审判。
- 门禁中 `BENCH_CMD` 缺失、静态检查缺失或性能命令本身只返回 0，都可能被报告为“审核完毕”，缺少基线数值对照和未验证清单。
- 没有把审查意见分类为采纳、拒绝、暂缓，也没有记录“拒绝的理由与证据”。
- UI 工作流的按钮、动效、音效规则带有全项目强制语气，可能与实时同传的低延迟、禁音、稳定性目标冲突。
- 旧版本由发布前的本地归档保存，不进入公开仓库；公开版本的历史以 Git 记录为准。

## 3. 实施设计

### 3.1 分层与文件边界

- **全局模板层（不随项目复制改写）**：三份工作流 MD、[`项目适配与契约初始化工作流.md`](./项目适配与契约初始化工作流.md)、[`项目契约模板.md`](./项目契约模板.md) 与 `scripts/`。
- **调用位置约定**：把工作流包整体复制到目标项目（或稳定维护一个绝对路径）后，从目标项目根目录调用工作流包的 `scripts/`，也可设置 `WORKFLOW_PACK_DIR` 指向全局包；`capture_baseline.sh`、`watchdog_gate.sh`、`fix_attempt.sh` 从当前项目读取契约、配置和基线。契约模板不嵌入仅在当前包内有效的相对文档链接。
- **项目契约层（随 Git 管理）**：目标项目中的 `.agents/PROJECT_CONTRACT.md`，以及按需要新增的 `.agents/decisions/ADR-*.md`、`.agents/fitness/` 回归资产。
- **本地过程层（不要求入库）**：`.agents/workflow.config`、`.agents/baseline/`、`.agents/fix-log/`、`.agents/expectations/`、`.agents/HANDOFF.md`、`.agents/snapshots/`。

`scripts/init_project_contract.sh` 负责初始化目录、本地忽略规则与不覆盖已有文件的 `workflow.config` 骨架；`scripts/capture_baseline.sh` 在动工前原子地锁定可信基线，失败不会替换上一份有效基线；`scripts/watchdog_gate.sh` 与 `scripts/fix_attempt.sh` 共同校验契约哈希、基线和证据命令一致性。

### 3.2 首次唤醒的项目适配

1. 先读取 README、入口文件、目录结构、测试、关键配置、既有 `AGENTS.md` 与 Git 历史；能由仓库回答的内容不重复问用户。
2. 生成带 `DRAFT` 状态的契约草案，所有推测明确标注 `[推断]`，并附证据路径。
3. 一次只问一个会改变规格、架构或验收的问题，最多 5 个；给出结构化选项与推荐，但用户可自由回答或豁免。
4. 候选维度不按项目名硬编码：同传关注稳定性、准确性、快速性及取舍；游戏关注可玩性、安全、输入响应；体验型前端关注审美、交流感、无障碍；其他项目先问核心价值与反目标。
5. 用户确认后把 `contract_status` 改为 `CONFIRMED`，补齐第一要义、质量排序、核心链路、保护项与证据命令，并纳入 Git。

### 3.3 修改前后的共同门禁

- **修改前**：契约必须为 `CONFIRMED`；运行 `capture_baseline.sh` 记录基线 SHA、测试状态、已知失败签名、核心回归、冒烟、静态检查与性能数值；基线不稳或命令缺失时不得宣称“零回归”。
- **理解代码**：只针对高风险、反直觉或核心路径记录“服务哪个目标、上下游依赖、为何这样写、禁止怎样简化、如何验证”，不要求逐行解释。
- **裁决建议**：每条审查建议必须有 `采纳 / 拒绝 / 暂缓` 结论、代码证据、对第一要义的影响和验证命令；与项目契约冲突时停止自动修改，呈交用户共商。
- **修改后**：看门狗在独立上下文中获得契约、相关设计原因、基线记录与净变更；验证目标修复、无新增失败、核心回归、冒烟、性能阈值和静态检查；最终报告必须列出“已修复、保持不变、尚未验证、已拒绝建议及理由”。
- **知识回流**：被证实的新设计原因、失败假设和防复发规则回填契约或 ADR；不把已证实有缺陷的实现永久保护起来。

### 3.4 证据与退出码

新增证据语义：`106` 契约或基线证据不足，`107` 基线本身不稳定，`108` 冒烟或核心回归失败。保留原有 `101`–`105`、`201`–`203`。`BENCH_CMD` 的最后一行必须输出一个数值；以 `BENCH_THRESHOLD` 百分比和 `BENCH_HIGHER_IS_BETTER` 比较基线，不再把“命令退出 0”直接当作性能达标。任何缺失命令都进入“未验证清单”，严格模式下不得输出“全绿”；显式豁免时输出 `PARTIAL` 并在交付报告中列明。

### 3.5 对既有三份工作流的调整

- **计划工作流**：Phase -1 前增加契约门；DoR 增加“契约已确认与基线已捕获”；Clarify 门增加质量优先级与反目标；看门狗输入包扩展为七件套；补充审查建议裁决与项目化交付报告。
- **修复工作流**：把契约和基线作为所有铁律的前置总律；分诊、侦探、主刀、第二意见均读取契约；期望卡增加“保持不变项”；白纸输入包扩展；出院报告记录拒绝建议与知识回流。
- **UI 工作流**：项目契约决定审美、动效、音效规则的适用范围；已有契约答案时不重复询问；通用 UI 组件库降级为候选来源；前端专项门禁按契约裁剪，不能压过项目第一要义。

## 4. 验证与验收

### 4.1 静态与脚本验证

- 对所有 Shell 脚本执行 `bash -n`；对初始化脚本、基线捕获、看门狗、修复记账执行隔离沙箱测试。
- 覆盖：契约缺失或仍为 `DRAFT`、契约在基线后改变、基线缺失、基线测试失败且无已知失败签名、已知基线失败未新增、证据命令或性能阈值在捕获后被改动、性能数值劣化超过阈值、性能命令缺失但 `PERF_CRITICAL=1`、显式豁免输出 `PARTIAL`。
- 验证未跟踪业务文件不能污染基线、失败重捕不会覆盖上一份有效基线、基准最后一行必须为数值、缺少核心/冒烟/静态证据只能显式 `PARTIAL`。
- 验证非 Git 项目目录快照退化与 dry-run、既有测试和既有复现脚本篡改审计、目标复现脚本逆转，以及初始化不覆盖既有 `AGENTS.md` 与本地配置。

已落地的回归脚本为 [`tests/test_project_aware_workflow.sh`](./tests/test_project_aware_workflow.sh)，在工作流包根目录运行 `bash tests/test_project_aware_workflow.sh`。它使用临时目录创建独立 Git/非 Git 项目，检查 Shell/JS 语法、契约模板初始化幂等性、草稿契约阻断、可信基线原子写入、契约与证据篡改、已知基线失败、显式豁免、现有复现测试保护和非 Git 回滚；脚本不会修改当前工作区中的业务文件。

### 4.2 场景验收

- **同声传译**：Agent 面对“统一加锁、增加同步等待、引入通用重试”的建议，必须先检查首字延迟、断流、乱序和长期稳定性；无证据时拒绝批量修改。
- **游戏**：契约以可玩性、安全、输入响应为优先；不套用同传或视觉动效验收项。
- **体验型前端**：契约可启用审美与交互门禁，也可因性能、无障碍或品牌约束裁剪通用组件库。
- **既有项目迁移**：从代码和文档生成草案，标记推断与确认，增量补充设计原因，不要求一次补完所有源码说明。

### 4.3 完成标准

1. `@` 任一工作流 MD 时，会先发现并加载项目契约；新项目会进入一次一个问题的初始化流程。
2. 契约未确认或基线不可信时，Agent 不得修改业务代码或宣布出厂。
3. 看门狗能基于项目目标与证据提出或拒绝建议，交付报告区分已验证与未验证。
4. 三份全局工作流保持通用，项目专属规则集中在 `.agents/PROJECT_CONTRACT.md` 及其 ADR、回归资产中。
5. 同传、游戏、前端三个示例场景均能生成不同质量排序，而不是复用一套固定优先级。

## 5. 已确认约定与边界

- 用户已确认采用“全局模板 + 项目契约”，不为每个项目复制并重写整套工作流。
- 用户已确认核心契约、关键设计原因和“可复现的基线定义”纳入 Git。基线定义包括稳定引用、真实证据命令、阈值和可复用回归测试；单次运行产生的数值清单、失败签名与过程日志保持本地。
- 质量排序由代码证据与用户共同确认，不预设“所有项目永远稳定性优先”。
- 契约保护的是高价值上下文与已确认的不变量，不保护已证实的缺陷，也不要求解释每一行源码。
- 本方案降低“局部正确、全局破坏”的概率，但不能替代真实项目里的代表性测试、监控和人工验收。
