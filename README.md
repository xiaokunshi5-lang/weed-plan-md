# WEED PLAN.MD

**English:** A Markdown workflow pack that helps coding agents keep a project's intent and evidence in view before they change code.

假设一次静态审查给稳定运行的同声传译项目挑出十处“不规范”：缓存、轮询、宽泛异常、兼容分支都在名单里。Agent 若逐条改完，代码可能更整齐，首字时延和断流恢复却可能退化。单看每一处修改都讲得通，连起来却可能碰掉这个项目最在意的两件事。

WEED PLAN.MD 就是为这类改动准备的。它让 Agent 在改代码前先读项目契约，在交付时把已配置的测试、核心回归、冒烟、静态检查和性能数值与稳定版本对照；缺项列入尚未验证。它是一组给 AI Agent 阅读的 Markdown 工作流、项目契约模板和少量本地脚本，目前是早期公开版本，不是框架、CLI 产品或自动重构工具，也不要求上传项目源码。

先读：[工作方式](#工作方式) · [第一次接入](#第一次接入) · [能力边界](#能力边界)

## 从一个熟悉的失败开始

一个已经稳定运行的版本，在静态审查里可能看起来“漏洞百出”。例如，审查意见可能要求把轮询改成阻塞等待，或清理兼容分支；要不要这样改，还得看契约中的实时性、降级恢复和旧状态兼容要求。通用最佳实践能提供线索，不能替项目决定这些取舍。

动手前先回答三件事：这个项目最不能失去什么，这段关键代码为什么这样写，用什么证据证明改动没有让系统变坏。WEED PLAN.MD 把它们写成文件、命令和门禁，让 Agent 在动手前读得到，在交付时绕不过去。

审查工具的每条意见只是待验证假设。结论必须是 `采纳`、`拒绝` 或 `暂缓`，并附代码证据和对项目首要目标的影响。缺少验证时只能报告 `PARTIAL`，不能冒充 `PASS`。

## 工作方式

首次接入要确认契约并捕获基线；后续任务在同一基线仍有效时直接读取，改动后逐条裁决、运行门禁并交付四栏报告，门禁失败则回到修改与裁决。

| 阶段 | 留下的文件或证据 | 谁拍板 |
| :--- | :--- | :--- |
| 只读调查 | README、入口、测试、配置和既有 Agent 指令里的线索，推断标记为 `[推断]` | Agent 调查，不替用户下结论 |
| 用户确认契约 | `.agents/PROJECT_CONTRACT.md`，状态从 `DRAFT` 变为 `CONFIRMED` | 用户确认第一要义、质量排序和保护项 |
| 稳定提交基线 | `.agents/baseline/` 中的稳定引用、测试状态、失败签名、证据命令摘要与性能数值 | 用户认可稳定 Git 引用 |
| 修改与裁决 | 每条审查建议的 `采纳 / 拒绝 / 暂缓`、代码证据和验证命令 | Agent 提出，用户裁决契约冲突 |
| 运行门禁 | `watchdog_gate.sh` 对契约、基线、新增失败、核心路径、性能和静态检查的结论 | 证据说话，缺项进入尚未验证 |
| 交付与回流 | 四栏报告；有长期价值的设计原因、失败假设和防复发检查写回契约、ADR 或回归测试 | 用户确认重大取舍 |

交付报告分四栏：`已修复`、`保持不变`、`尚未验证`、`已拒绝建议及理由`。没有证据的项目留在第三栏，不拿局部绿灯凑成 `PASS`。

## 项目契约：先问「为什么」

全局模板不预设“稳定性、速度、美观”谁永远第一。进入项目后，Agent 先读 README、入口文件、测试、配置和既有 `AGENTS.md`，再打开 [`项目适配与契约初始化工作流.md`](./项目适配与契约初始化工作流.md)，把结论写进 `.agents/PROJECT_CONTRACT.md`。能从仓库确认的写 `[已验证]`，推测写 `[推断]`；只有用户拍板的才写 `[已确认]`。

契约记录了项目最不能失去什么、有顺序的 P1–P3、核心链路、反直觉设计的原因、已知失败、证据命令和 UI 规则适用范围。修改单看不够标准的实现前，Agent 要查清它服务的契约目标、上下游和对照证据。只有契约和证据确认后才按保护项处理，已证实是缺陷的实现照样修改。

| 场景 | 可能被确认的首要维度 | 一次具体取舍 |
| :--- | :--- | :--- |
| 同声传译 | 连续可用、准确性、首字与端到端时延 | 为提升准确率增加等待，是否越过实时性底线？ |
| 游戏 | 可玩性、安全性、输入响应 | 防作弊校验是否可以牺牲操作手感？ |
| 体验型前端 | 审美、交流感、无障碍、首屏代价 | 动效与素材体积是否损害可用性？ |

这些只是启发示例，不按目录名套用固定答案。Agent 一次只问一个会改变质量排序或验收的问题，用户确认后才把契约改为 `CONFIRMED`。长期契约、ADR 和可复用回归资产纳入项目 Git；`workflow.config`、数值基线、修复日志、交接单和快照默认留在本地。流程与契约冲突时，Agent 停下来呈交代码证据、候选方案和各自代价，由用户裁决。

## 可信基线：留下可复核的对照

基线记录用户认可的稳定 Git 引用，以及那一刻的测试状态、失败签名、证据命令摘要和性能数值。后续改动与这份记录对照，才能讨论「有没有变坏」。

[`capture_baseline.sh`](./scripts/capture_baseline.sh) 要求契约已 `CONFIRMED` 且纳入 Git、无占位符、HEAD 与稳定引用一致、已跟踪文件无未提交改动，并拒绝 `.agents/` 之外的未跟踪业务文件；未配置的证据项留待门禁列为尚未验证。它先写进暂存目录，全部成功后才替换上一份基线；一次失败的重捕不会毁掉旧基线。契约哈希、证据命令、性能阈值和指标方向会与基线绑定，改动后需要重新捕获。

| 结论 | 含义 |
| :--- | :--- |
| `PASS` | 已验证项通过，没有把缺失证据写成豁免 |
| `PARTIAL` | 用户明确记录 ADR、设置 `ALLOW_UNVERIFIED=1` 且缺口可豁免时，保留未验证清单 |
| 非零退出 | 门禁指出具体缺口，例如新增失败、性能退化、契约或基线被改动 |

证据命令填在本地 `.agents/workflow.config`。`BENCH_CMD` 的最后一行只能输出一个数值；`true` 和 `exit 0` 不能冒充证据。性能阈值、指标方向和 `PERF_CRITICAL` 在基线后改变时必须重新捕获基线。

## 一次改动的裁决

假设审查建议是：“把实时链路里的轮询改成同步等待，少一段状态管理。”Agent 不直接开工，先把建议放进契约的裁决表。下表演示的是一条建议如何写进裁决表，`采纳`、`拒绝` 或 `暂缓` 仍要结合代码证据、契约 P1–P3 和用户决定：

| 建议 | 裁决 | 需要写下的证据 |
| :--- | :--- | :--- |
| 把轮询改成同步等待 | `拒绝` 或 `暂缓`，取决于是否有首字时延和断流恢复的对照实验 | 契约 P1、上下游调用链、性能数值、核心路径回归结果 |
| 把宽泛异常收窄 | 有失败签名、复现测试且不破坏契约时才可能 `采纳` | 目标修复、契约 P1–P3、无新增失败、静态检查结论 |

每条建议都要回答：它对 P1 有什么影响，哪条命令能验证，是否需要写 ADR。“更符合最佳实践”本身不是理由。一次微创尝试只验证一个根因假设；[`fix_attempt.sh`](./scripts/fix_attempt.sh) 记录重复假设和代码震荡，[`rollback.sh`](./scripts/rollback.sh) 在需要时保留救援分支并退回稳定版本。

## 看门狗门禁

看门狗在独立上下文中运行 [`watchdog_gate.sh`](./scripts/watchdog_gate.sh)；脚本读取契约、`.agents/workflow.config` 与基线记录，并按基线标签检查测试、证据文件改动、新增失败、核心路径、性能和静态检查。

默认有未验证项就以非零退出码阻断，只有用户已记录 ADR、设置 `ALLOW_UNVERIFIED=1` 且缺口可豁免时才报 `PARTIAL`；`PERF_CRITICAL=1` 却没有 `BENCH_CMD` 会直接以 `103` 失败。门禁提出的是待验证假设，逐条裁决后才会进入下一轮修改。没有跑过的项目留在「尚未验证」，不靠措辞补上。

被拒绝且有长期价值的理由，比一次顺手的修改更值得留下：把设计原因回写契约，把失败假设和防复发检查写进 ADR、`.agents/fitness/` 或回归测试。过程日志留在本地；已证实的缺陷不许借“历史原因”继续受保护。

## 第一次接入

先在副本里试跑。环境需要 Bash、Git、Node.js（仅用于检查可选的 UI 脚本）；工作流脚本主要在类 Unix 环境验证，正式可信基线要求目标项目是 Git 仓库。

```bash
git clone https://github.com/xiaokunshi5-lang/weed-plan-md.git
cd weed-plan-md
bash tests/test_project_aware_workflow.sh
```

进入你的目标项目，把本仓库作为工作流包使用：

```bash
cd /path/to/your-project
WORKFLOW_PACK="/path/to/weed-plan-md"
"${WORKFLOW_PACK}/scripts/init_project_contract.sh"
```

接着按这个顺序操作：

1. 打开 [`项目适配与契约初始化工作流.md`](./项目适配与契约初始化工作流.md)。Agent 先读 README、入口、测试、配置和既有 Agent 指令；遇到会改变质量排序或验收的未知项，停下来一次问用户一个问题。
2. 填写 `.agents/PROJECT_CONTRACT.md` 第 1 至 8 章，删除全部 `{{...}}` 占位符。用户确认后，把 `contract_status` 改为 `CONFIRMED`，并将契约、ADR 和可复用回归资产纳入项目 Git。
3. 把真实测试、核心回归、冒烟、静态检查和性能命令填入本地 `.agents/workflow.config`。不要用 `true` 或 `exit 0` 冒充证据。
4. 在用户认可的稳定提交或标签上捕获基线：

```bash
"${WORKFLOW_PACK}/scripts/capture_baseline.sh <stable-tag-or-commit>"
```

5. 日常按 [任务入口](#任务入口) 打开对应的全局工作流；契约已经回答的问题不重复问。

工作流包也可以整体复制到目标项目，此时上述 `WORKFLOW_PACK` 可替换为项目内相对路径。长期契约和 ADR 属于项目仓库；`workflow.config`、数值基线、修复日志、交接单和快照默认保持本地。

> [!NOTE]
> 脚本会读取本地 `.agents/workflow.config`，通过 `bash -c` 执行你填写的证据命令。部分脚本会创建 Git 提交、标签、救援分支或执行回滚。先读脚本、保留独立备份，并用 `--dry-run` 预演回滚；不要在唯一一份工作区里第一次试用。

## 能力边界

这套流程降低「局部正确、全局破坏」的概率，但不保证零回归，也不能替代代表性测试、监控和人工验收。契约质量取决于真实证据和用户确认；自动探测到的内容必须标注为推断，不能伪装成结论。

正式可信基线要求 Git 锚点。非 Git 目录仅支持目录快照回滚，不能作为正式可信基线。主要脚本和回归测试在类 Unix 环境验证，Windows 原生环境尚未纳入测试矩阵。

参考的开源项目用于说明设计灵感，不代表它们参与维护或背书本仓库。复制 UI 片段前须逐项核验其当前许可。
